NVIDIA/SkillEvaluatorPythondeep

该项目用命令行和可复用持续集成工作流对智能体技能做分层检查：第一层静态验证质量、安全与兼容性，第二层做语义去重，第三层在容器沙箱和模型端点中比较有无技能的影响，并输出评分报告与合并门禁。

实现逻辑

Q1 · 命令行和 CI 的入口如何串起来？

README 提供 skillevaluator validate、harness-check、quality-check、tier2、tier3、ci init 和 doctor 等命令。ci/bundles/1.0.1/skill-checks.yml 在 pull_request、push 和 workflow_dispatch 上复用 .github/workflows/evaluate-skills.yml，并传入 image、paths、min-score、scan-mode 等参数。ci/run_tiers.py 与 ci/bootstrap_tiers.py 的路径表明 CI 侧还负责分层启动和依赖准备。

来源：README.md ci/bundles/1.0.1/skill-checks.yml .github/workflows/evaluate-skills.yml ci/run_tiers.py ci/bootstrap_tiers.py

Q2 · 三层检查在结果组合和门禁上有什么区别？

README 说明每个 tier 独立运行，validate 默认组合三层检查。Tier 1 作为基础门禁，Tier 2 默认也能阻断，除非使用 --no-block-on-dedup，Tier 3 需要显式 --block-on-agent-eval 才参与门禁。quality-check 只做静态评分，默认阈值 70，并会把 publication evidence 标为 INCOMPLETE；如果 scanner 无法运行，结果也是 INCOMPLETE 且退出码非零。

来源：README.md docs/tier1-validation.mdx docs/tier2-deduplication.mdx docs/tier3-live-evaluation.mdx

Q3 · 外部依赖和第三方工具如何被引入？

README 将 Tier 1 扩展到 SkillSpector、Gitleaks、Bandit、可选 Semgrep 和 pip-audit，并将 Tier 3 扩展为 Harbor sandbox、NVIDIA Build endpoints 与 LLM/chat/embedding provider。ci/requirements/skillspector.txt 和 ci/requirements/semgrep.txt 显示 CI 侧对部分 scanner 依赖有单独锁定文件。ci/bundles/1.0.1/skill-checks.yml 使用按 digest 固定的 ghcr.io/nvidia/skillevaluator-tier1 镜像，使 scanner 运行环境可复现。

来源：README.md ci/requirements/skillspector.txt ci/requirements/semgrep.txt ci/bundles/1.0.1/skill-checks.yml

Q4 · harness compatibility 和 live evaluation 分别验证什么，需要什么前提？

harness-check 根据 versioned profiles 判断 codex、claude-code、opencode 等是否能加载技能，不需要 API key 或真实 agent run。Tier 3 需要 provider、supported agent 和运行中的 Docker sandbox，用来比较带技能与不带技能的任务结果。create-eval-dataset 可用 evals/EVAL.md、--prompt 文件或 retained traces 生成评测用例，autopilot 在无现有 source 时只创建一个 starter case。

来源：README.md docs/harness-check.mdx docs/tier3-live-evaluation.mdx docs/prepare-dataset.mdx

Q5 · 安全、隐私和报告处理在哪些文件中体现？

README 把 PII、license、Unicode、security 和 code integrity 归入 Tier 1 检查，并列出 SkillSpector、Gitleaks、Bandit 和 Semgrep。仓库根目录有 .gitleaks.toml 和 .gitleaksignore，说明 secret scanning 配置被纳入项目自身治理。ci/secret_redaction.py 与 ci/security_baselines.py 的路径表明 CI 侧还有脱敏和安全基线处理，但 skill-checks.yml 默认 security-baselines: false。

来源：README.md .gitleaks.toml .gitleaksignore ci/secret_redaction.py ci/security_baselines.py ci/bundles/1.0.1/skill-checks.yml

技术栈
Python / GitHub Actions, GitLab CI, Docker, Harbor, NVIDIA Build / pip install skillevaluator; Makefile 通过 pytest、ruff 和 python -m build 管理开发构建
适用场景
  • 在 GitHub 或 GitLab CI 中对 Agent Skills 目录做静态质量与安全门禁
  • 诊断技能是否能被不同 agent harness 加载，以及哪些 profile 会导致 degraded 或 not loaded
  • 检测多个技能之间说明重复或语义重叠，减少 catalog 内部冲突
  • 在 Docker sandbox 中运行 agent，比较带技能和不带技能的任务表现
  • 生成或精修评测数据集，用于持续评估技能效果
风险
  • README 标明支持级别为 Experimental，没有 SLA 或 NVIDIA enterprise support entitlement
  • 完整 Tier 1 静态检查依赖 SkillSpector、Gitleaks、Bandit、可选 Semgrep 等外部 scanner
  • Tier 3 live evaluation 需要 provider、supported agent、Docker，并可能涉及模型或 managed sandbox 费用
  • CI template 默认 security-baselines: false，需要 reviewed baseline manifest 到达目标分支后再启用
  • NVIDIA Build endpoints 有 access terms 和 rate limits，doctor 检查 readiness 不等于 inference 一定成功
  • 项目会下载并安装第三方 open source software，用户需自行审阅对应 license terms

cursor/pluginsTypeScriptdeep

实现逻辑

Q1 · 这个仓库如何组织插件并让 Cursor 识别？

根目录 README 说明每个插件都是独立目录，目录内用 .cursor-plugin/plugin.json 作为 manifest；目录树显示 manifest 旁边常见 agents、skills、hooks、rules 等资源目录。仓库根还有 .cursor-plugin/marketplace.json，第三方插件集中在 third_party 下，形成集中索引加独立子包的布局。

来源：README.md .cursor-plugin/marketplace.json advisor/.cursor-plugin/plugin.json

Q2 · watch-pr 脚本的入口与调用链是怎样的？

cli.ts 的 main 先调用 parseArgs，使用 Commander 生成 CliOptions，再选择 renderJson 或 renderPretty 作为输出函数。随后它通过 realRuntime 注入 reader、clock 和 stdout/stderr，调用 resolveContext 获取起始 PR 上下文，必要时用 discoverStack 扩展为 stack，最后把 mode 分派给 runQueued 或 runSimple。

来源：harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/cli.ts harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/github.ts harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/policy.ts harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/render.ts

Q3 · 脚本如何区分 single、stack 和 queued-stack 等核心状态？

CliOptions.mode 由 --queued-stack、--stack 或缺省决定；stackPrs 保存 --stack-prs 传入的冻结队列，statusOnly 控制只打印一次状态。polling 子对象集中承载 interval、sweepInterval、timeout、maxQueryErrors 和 allowDraft，runQueued 与 runSimple 分别消费这些参数。worker.md 还定义了外部 agent 运行规则，例如默认不向人提问、PR 以可审查状态打开，说明脚本服务于可自动化 agent 流程。

来源：harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/cli.ts harness/pstack/claude-code/skills/poteto-mode/worker.md

Q4 · 外部依赖、错误处理和可测试性是如何设计的？

脚本直接依赖 commander 和 Node 的 timers/promises，并通过 CliRuntime 把 GitHub reader、clock、stdout/stderr 注入 main，便于测试替换；package.json 将 type 设为 module，并提供 bun test 与 tsc typecheck。参数错误由 Commander 的 InvalidArgumentError 或 Command.error 转成退出码 64，查询错误 WatcherQueryError 则转成 statusQueryVerdict，保持输出为 JSON verdict。

来源：harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/cli.ts harness/pstack/claude-code/skills/poteto-mode/scripts/package.json harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/github.ts harness/pstack/claude-code/skills/poteto-mode/scripts/watch-pr/policy.ts
