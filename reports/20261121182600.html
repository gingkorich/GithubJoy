Codex Security 是面向开发、安全和审计人员的代码漏洞工作流工具。它能在仓库、指定目录或 Git 改动范围里扫描安全风险，也可在 Codex 对话、终端、TypeScript SDK、GitHub Action 或容器里自动运行。使用者可以找鉴权、依赖、注入等候选问题，生成补丁或验证已有修复，还能起草 SECURITY.md、保存威胁模型、导入第三方扫描器结果并导出 SARIF/JSON/CSV。它特别强调本地扫描、证据保存、去重、严重性评级、负责人建议和可选 Codex Security Cloud，把单次漏洞检查扩展成可审计、可复用的安全流程。

实现逻辑

Q1 · 用户从哪些入口启动扫描，并且后续动作怎样被调用？

普通终端使用 cs scan 或 codex-security scan 指定仓库路径，可带 --path、--exclude-path、--diff、--mode deep 等参数控制范围。自动化代码里安装 npm 包后导入 CodexSecurity，调用 security.run(repository) 得到 reportPath，并显式 close。CI 可通过 GitHub Action 工作流或 Docker Compose 批量运行，README 中的示例使用 CODEX_SECURITY_API_KEY 和每周 ubuntu job。评测脚本还展示另一种底层调用方式：通过传入 JSON 的 CLI 进程执行 run init、run next、run record-claims 等命令。

来源：README.md evals/dependency-reachability/run.mjs

Q2 · 扫描结果如何被保存、找回和跨工作树复用？

扫描完成会保存 report 和 findings，Markdown report 路径在终端 REPORT 提示里；同一仓库可用 cs scans show 找回最新完成扫描。链接工作树通过保持 CODEX_SECURITY_STATE_DIR 稳定，可以共享扫描历史和 sign-in scope。评测中的 initialize 调用 run init 时把 --state 指向一个 sqlite 文件，把 --inputs 指向准备目录，后续 next、read、record、finalize 都围绕这个 state 操作。finalize 返回 runId 和 attemptId，报告再交给 gradeStack 判定。

来源：docs/project-configuration.md evals/dependency-reachability/run.mjs

Q3 · finding、claims、receipts 等核心数据如何关联到一次工作流？

核心工作对象包括 workItem、receipt、claim、assessment 和 report。run next 返回 workItem 和 receiptId；read-stacks 可把 observation.frames 补成 observation.bindings。record-claims 接收带 id、scope、payload 和 receiptSelections 的 claims，并返回包含 revision 和 hash 的记录。record-assessments 用 verdict、reason 和 supportingClaims 关联结论；如果篡改 receipt 中的捕获选择，gradeStack 会拒绝。

Nutlope/hallmark★ 58,803

Hallmark 是一个给 Claude Code、Codex、Cursor 和 OpenCode 使用的前端设计 skill，用来让 AI 生成或重做网页时少一点模板味，多一点可交付感。工程师可以直接对它说做一个预约页、给本地应用重做首页或审计这个页面，它会先读取或询问真实材料，再围绕用户要完成的事情安排按钮、表单、图片和文案，并输出一份独立的 HTML 与 CSS。它适合落地页、作品集、商店、预订、新闻信和 API 介绍这类常见小站，也可以只报告问题而不改动。它的特别之处是有五十个视觉素材、多种宽度的浏览器检查，以及会避免假提交、空图片框、每页邮箱订阅等一眼像模型生成的痕迹。

实现逻辑

Q1 · 这个 skill 的入口在哪里，一次典型构建会经过哪些主要步骤？

安装后它作为 Claude Code、Codex、Cursor 或 OpenCode 的 skill 被调用，用户通常输入 /hallmark <prompt> 或 $hallmark <prompt>，也可以让工具根据描述自行触发。构建阶段会先读取项目字体、配色、框架和已锁定的 design.md，再调用 skills/hallmark/scripts/theme.mjs 推荐主题并从页面任务生成结构。页面生成后用 skills/hallmark/scripts/sloplint.mjs --render 在真实浏览器里检查多个宽度，最后由新上下文的 reviewer 给出意见。

来源：README.md

Q2 · 五十个主题在仓库里主要以什么形式存在，生成页面时如何消费它们？

README 说每个主题位于 skills/hallmark/references/themes/，是至多 8 KB 的材料文件，只规定纸张、字体、颜色、表面和纹理，不规定页面内容和顺序。每次构建只读取一个主题，所以同一主题面对不同 brief 会生成不同页面。仓库里的 site/themes 和 site/made 目录提供了这些主题的示例页面，常见形式是自包含 HTML 加上 style.css、base.css、tokens.css 和少量脚本。

来源：README.md site/themes/cobalt/index.html

Q3 · 视觉 lint 和截图检查依赖哪些外部工具，缺少它们时会怎样？

安装使用 npx skills add nutlope/hallmark，需要 Node 18 或更高版本。sloplint --render 和页面截图还需要全局安装 puppeteer-core 以及 Chrome；没有它们时，静态检查仍能运行，但浏览器渲染检查不能完整使用。

来源：README.md

Q4 · 它如何处理已有页面重设计和审计，避免把原有功能弄丢？

重设计和审计通过 /hallmark redesign <path> 与 /hallmark audit <path> 触发，前者会重建页面但保留内容与接线，后者只报告。在动手前，sloplint --before 会先记录链接、表单字段、事件处理和标题等原有功能；重做后用 sloplint --kept 检查是否缺失，如果少了就失败。交接时还会给出前后对比，避免只改视觉导致行为回退。

来源：README.md

Q5 · 哪些检查会直接阻止交付，哪些只是建议？

README 把门槛分成 Floor、Reflex 和 Finish：Floor 涉及对比度、焦点、减少动效、虚构事实、手机布局断裂等底线问题，永远不允许 ship。Reflex 是模型容易落入的默认毛病，如果有明确理由可以在记录后覆盖；Finish 是工艺细节，不会阻止交付。实际 lint 会寻找 eyebrow 标题、全大写标签、只给一句感谢却没有提交动作的表单、每页末尾邮件订阅等常见痕迹。

来源：README.md

Q6 · 为什么选择 Wikimedia 照片而不是 Unsplash、Pexels 或 Pixabay？

项目把照片库放在 skills/hallmark/scripts/photos.json，里面只列 Wikimedia Commons 上开放许可图片的条目，仓库本身不保存图片文件。README 说明它不使用 Unsplash、Pexels、Pixabay，因为这些平台的条款不允许 AI 工具选择其图片。使用 Wikimedia 素材时，每个页面会给实际用到的照片署名。

pingdotgg/t3code★ 68,535

T3 Code 是一个本地优先的编程 agent 控制面板：它在你自己的电脑上驱动已经登录好的 Claude Code、Codex、Cursor 等 agent，并通过桌面端、Web 和手机提供同一个线程视图，方便你启动任务、批准下一步命令、切换模型，或让一个 agent 把任务交给另一个 agent。它适合已经使用编程 agent，但希望远程操控、权限审批、Git 工作流和团队协作更顺手的开发者；每个线程可以放在独立 worktree 里，支持查看 diff、提交、推送和创建 PR。项目不转售 token，不依赖厂商托管 agent，强调性能、开源 MIT 授权，并可通过本地网络、Tailscale 或 T3 Connect 远程连接。

实现逻辑

Q1 · 用户从哪里启动 T3 Code，启动后大致经过哪条调用链？

基于 README 的安装说明，桌面端可以直接运行应用，命令行 `t3` 会启动本地 server 并打开 Web app。server 作为统一控制平面保存线程状态，桌面、Web 和手机客户端都连接同一 server 查看和审批线程。实际执行编程任务时，T3 会调用本机已经安装并登录的 agent，例如 `claude auth login` 或 `codex login` 后的 CLI。

Q2 · 多端同步和远程连接是怎么组织的？

README 强调 One server, and every client shows the same threads，所以关键不是每个客户端各自跑 agent，而是本地或远端机器上的 server 维护 thread/session。用户可通过本地网络、Tailscale 或 T3 Connect 把手机连接到运行 agent 的机器。这样线程创建、命令审批、diff 查看和状态更新可以在不同设备之间保持一致。

Q3 · 它如何接入不同 agent？

README 把 ACP 作为 provider 接入文档入口，说明 T3 优先通过 Agent Client Protocol 这类标准接口控制已安装的 coding agent，例如 Claude Code、Codex、Cursor 等。对外部 agent 或工具，README 又指向 MCP 文档，因此 T3 本身更像控制平面，用标准协议把本地 agent 会话纳入同一 UI。

Q4 · Git worktree 与线程隔离在实现上怎么体现？

README 说明每个线程可以工作在独立 worktree，便于 review diff 后提交、推送和创建 PR。仓库内的 `pr-queue` skill 给出了更具体的调用形态：`t3_thread_launch` 可以传入 `workspaceStrategy: { type: 'worktree', baseRef: 'origin/main' }`，为每个任务创建自己的 checkout。这样每个 agent thread 修改文件时不会互相踩工作区，线程完成后再由人决定 merge。

来源：.repos/alchemy-effect/.agents/skills/pr-queue/SKILL.md

Q5 · 多 agent 线程并发运行、PR 队列协调是如何避免冲突的？

`pr-queue` skill 要求每个工作项用 detached top-level thread，而不是 subagent，使每个线程能独立等待 CI 并直接向用户请求 merge/close。启动 worktree 线程时分批约 3 个进行，避免很多线程同时切 worktree 竞争 git 锁。协调者维护状态表和 thread link，实际修复由 item thread 完成，减少单一协调线程成为瓶颈。

来源：.repos/alchemy-effect/.agents/skills/pr-queue/SKILL.md

Q6 · 权限审批在控制链里扮演什么角色？

README 的 hero 描述展示手机上批准 Codex 下一步命令，docs 也有 permission modes，说明 T3 把 agent 的高风险操作作为可审批的 thread step。用户可以在桌面、Web 或手机确认命令、diff 或下一步，agent 再继续执行。基于给定材料，具体权限模式枚举和默认值无法确认，需要看 `docs/user/permission-modes.md`。

OpenMausBot 是一个桌面端 AI bot 聊天应用：侧边栏每个 bot 都像联系人，背后调用本机 Claude、Codex 或 Grok 等命令行智能体。用户可以在聊天里为 bot 切换模型、分配任务、流式查看回复与工具过程，并批准 shell 命令或文件编辑；每个 bot 还能连接 Gmail、Slack、GitHub 等应用，或使用云端 Linux 桌面和本地 VM。它把对话记录、配置和密钥放在本地 ~/.openmausbot，支持导入团队 playbook、语音朗读、无头 CLI 和 MCP 控制接口。它不是只给单个模型加聊天框，而是把多个可编排 agent 做成类似消息软件的工作台：可以创建频道、设置共享指令、复制 bot、查看审批卡片，也能通过脚本或外部 MCP 客户端查询、发送任务和等待完成，适合想用本地优先方式组织多个智能体的工程师和小团队。

实现逻辑

Q1 · 应用和 agent 的入口与调用链是怎样的？

根据 README 的两进程架构，React/Electron 前端不直接连模型，只向 127.0.0.1:8799 的 harness server 发 typed HTTP commands。harness 的 drivers registry 根据配置启动或复用本地 claude、codex、grok 等 CLI，再把每个 CLI 的 stream-JSON、JSON-RPC 或 ACP 输出归一化成统一 runtime event stream。前端通过一个 SSE 事件流把消息、工具运行、审批等状态折叠成界面状态。

来源：README.md

Q2 · 核心数据结构是什么，怎样表示一次 bot 对话和外部连接状态？

README 说每个线程的 transcript/events 以 NDJSON 持久化在 ~/.openmausbot，harness 同时维护 registry，把 provider configs 映射到 live agent instances。Composio broker 文件里也有一个核心会话结构：Zod 校验 session_id、mcp.url、headers、multi_account 和 auth_configs，再归一成 sessionId、url、headers、authConfigs 等字段。这样上层 bot 的运行状态和外部应用连接状态都先被收敛为可重放的结构化事件。

来源：README.md cloudflare/composio-broker/src/index.ts

Q3 · 外部服务接口怎么接入，尤其 Composio connected apps？

cloudflare/composio-broker/src/index.ts 只接受 https 且 host 为 composio.dev 或子域的 MCP URL，并过滤 Host、Cookie、Content-Length 等 header，防止 session 指向任意端点。它用 createSession 创建带 manage_connections 和 multi_account 配置的会话，再用 getSession 查询和复用，并把 auth_configs 按 toolkit slug 规范化。这样 Gmail、Slack、GitHub 等应用通过一个 broker 进入，bot 不直接持有上游地址和 header。

Q4 · 权限、审批和安全边界在哪里实现？

README 的 permission broker 把 shell command、file edit、question 等风险动作变成聊天中的 Allow/Deny/answer 卡片，云端和本地 computer 都走同一 broker。MCP server 明确限制工具面：只读取或操作 bots、channels、transcripts、tasks、models 和 interrupt，不暴露 approval grants、deletion、settings、credentials 和 computer lifecycle。Composio broker 还做 alias 长度和可打印字符校验、canonical slug 映射，并限制请求 body 大小，减少输入污染。

Q5 · 本地优先状态持久化和失败降级怎么处理？

会话记录、API keys 和事件都写到本地 ~/.openmausbot，App Settings 里的密钥是写-only，UI 只看到 configured flags。README 说 unknown drivers 会降级成 unavailable，而不是让整队 agent 崩溃；Composio broker 也用 upstreamError 把非 2xx 的响应转换成可展示的错误。这样单机故障、缺失 CLI 或上游返回异常时，应用可以标记对应 provider 或连接不可用。
