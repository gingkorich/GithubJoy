GoogleChrome/modern-web-guidance-src★ 9,314

这个项目是 Modern Web Guidance 的源码仓库，用来制作、校准和评估一组给 AI coding agent 使用的网页平台技能。它主要面向前端开发者、维护现有项目的团队，以及借助 AI coding agent 写网页代码的人；用户可以运行 npx modern-web-guidance 安装向导，也可以不安装而用 search、retrieve、legacy-scan 命令查询指南、获取指定文档或扫描旧式写法。它的作用是把现代浏览器 API、性能、无障碍和浏览器兼容建议放进 agent 上下文，帮助模型少沿用训练数据里的老旧模式、重量级 polyfill 或废弃接口，而转向 View Transitions、Popover、Container Queries、Built-in AI 等原生能力，并强调轻量、更省 token、经 eval 校准。

backnotprop/plannotator★ 13,745

Plannotator 是一个给使用 AI 编程代理的工程师和团队用的本地审阅工作台，解决代理自动产出计划、代码改动、Markdown 文档、HTML 原型或站点后，人需要集中查看、标注并把意见准确送回代理的反复循环问题。它不试图替代编辑器或终端，而是在浏览器里提供计划审批、差异/PR 审查、文件/URL/localhost 实时标注、Inbox 收件箱和可分享审阅链接等界面，支持多种代理接入；当代理请求退出计划模式、完成一轮工作或用户执行相应 slash 命令时，本地服务会打开对应页面，用户直接在正文、行号、diff 或选择项上批注，再把结构化反馈交给代理继续修订，适合个人快速回看代理结果、团队共享评审意见，以及把多代理输出集中到一个可回复窗口。

实现逻辑

Q1 · Plannotator 怎样接进 AI 编程代理并把反馈送回？

README 描述它通过 plugins、hooks 和 commands 接入各类 agent：当 agent 提出计划、产出文档或完成一轮工作时，本地服务打开浏览器审阅页面。用户批准或拒绝计划后，反馈会送回 agent；在 DSH 插件示例中，plan review 接到 exit_plan_mode，同时注册 plannotator_inbox 工具和命令，审阅打开后立即返回，用户决定再作为新 turn 回到会话。

来源：README.md apps/dsh-plugin/index.ts

Q2 · DeepSeek Harness 插件调用本地 plannotator CLI 的关键路径是什么？

apps/dsh-plugin/cli.ts 先用 resolvePlannotatorBinary 按配置项、PLANNOTATOR_BIN、PATH 和常见安装目录查找可执行的 plannotator。随后 runDshPlan 以子进程运行 plannotator dsh-plan，把 plan JSON 写入 stdin，stderr 用于回传 URL，stdout 最后一行 JSON 被解析为 approved、feedback、message、savedPath 等字段。启动失败、非零退出、缺少 JSON 或 abort 会走各自的错误路径。

来源：apps/dsh-plugin/cli.ts

Q3 · Cline 插件如何维持会话状态同时避免破坏宿主运行？

apps/cline-plugin/index.ts 在每个 session worker 的 setup 中调用 setupClineInbox，保存一个 ClineInboxSession，并用 beforeRun 和 afterRun hooks 同步会话忙碌状态。该文件强调每个 setup 和 hook 都被 try/catch 保护，集成错误只记录或忽略，不向 Cline 抛出，从而把 Plannotator 的连接失败影响降到最低。

来源：apps/cline-plugin/index.ts

Q4 · 代码 review 和 guided review 的大致调用链是什么？

README 的 How it works 显示，/plannotator-review 会先用 git diff 捕获本地未提交改动，或按 GitHub/GitLab URL 拉取 PR/MR，然后在浏览器中打开带文件树和 side-by-side diff 的审阅界面。用户在行上批注、stage/unstage 文件后，评论会送回 agent；guided review 再叠加一层 agent 辅助，把大 diff 排序成多个 chapter，概述和真实 diff 并列展示。

来源：README.md adr/specs/guided-review-20260702-195351.md

Q5 · 共享和持久化是怎么拆分的？

README 说 sessions 和 archive 用于本地会话与历史，终端和 app 的标注保存在 Plannotator data directory，小型分享直接编码进链接，大型分享会加密上传并在 7 天后过期，PLANNOTATOR_SHARE=disabled 可关闭。目录结构中出现 apps/feedback-service/core/handler.ts、apps/feedback-service/stores/d1.ts 以及 apps/guides-show/share/stores/r2.ts，基于 README/目录结构推断，云端分享处理和存储被拆到独立服务模块中。

来源：README.md apps/feedback-service/core/handler.ts apps/feedback-service/stores/d1.ts apps/guides-show/share/stores/r2.ts

Q6 · 错误处理上能看到哪些设计取舍？

apps/dsh-plugin/cli.ts 对子进程输出做了保守解析：只取 stdout 最后一行 JSON，要求 approved 是布尔值，非零退出时用 stderr 最后一行作为错误信息，abort 时先 SIGTERM 再 SIGKILL 并等子进程退出后才 settle。apps/cline-plugin/index.ts 则选择吞掉插件内部异常，确保宿主 agent 不被打断；这类取舍优先保证 agent 工作流连续运行，但会让本地配置错误更不容易立刻暴露。

来源：apps/dsh-plugin/cli.ts apps/cline-plugin/index.ts

meta/astryx★ 31,140

Astryx 是面向 React 应用的开源设计系统，解决团队既要快速搭 UI、又容易被样式框架和组件黑盒绑住的问题。它提供大量可访问组件、主题、模板和命令行工具，适合前端工程师、设计系统和 AI 编程助手一起使用。常见用法是安装核心包、导入 CSS、套一个主题提供者，然后直接用组件；需要定制时可以用 className 接 Tailwind 或普通 CSS，也可以用 CSS 自定义属性做品牌主题。它的特别之处是把 API、文档、CLI 和面向助手的说明设计成同一套，让人和 AI 用同样方式查询组件、生成模板或检查项目。

实现逻辑

Q1 · 这个项目从哪里进入，用户怎样开始使用它？

核心入口是 @astryxdesign/core 包，它承载组件、主题系统和工具，用户安装 core、主题和 StyleX 后导入预编译 CSS，并在应用根部套上主题提供者。首次集成可由 @astryxdesign/cli 的 init 命令完成，它会打印起步说明并把指南写入 AGENTS.md/CLAUDE.md，供人和代码助手共同读取。实际开发时再 import 具体的 TypeScript 组件，而不是先配置 StyleX、PostCSS 或 Babel。

Q2 · 样式是怎么实现，又如何避免绑定某个 CSS 方案？

Astryx 内部用 StyleX 书写组件样式，但发布的是可直接导入的预构建 CSS，使用方不需要采用 StyleX、Babel 或 PostCSS 插件。覆盖时主要通过组件的 className 接入 Tailwind、CSS modules 或普通 CSS，让已有项目的样式体系继续工作。主题层则通过 CSS custom properties 暴露颜色和字体等可调值，因此品牌化通常不要求替换组件实现。

Q3 · 主题、暗色模式和可定制部分在仓库里怎样组织？

主题由 @astryxdesign/core 的主题系统提供能力，@astryxdesign/theme-* 提供多套预置主题，例如 neutral、butter、chocolate、matcha、stone、gothic、y2k。定制时不是 fork 组件源码，而是写一组 CSS custom property 覆盖，因此一个主题可以改变视觉而不侵入组件内部。暗色模式和品牌化也沿着这套变量与 provider 的方式暴露给应用。

Q4 · CLI 在项目开发流程里承担什么角色？

@astryxdesign/cli 不只是安装脚本，它把组件文档、模板、scaffolding、themes 和 codemods 做成统一入口，供人和 AI 在同一份 reference 下查询与生成。init 会引导样式、主题接入，并生成 AGENTS.md/CLAUDE.md；后续还能通过 npm script 调用本地 CLI，降低助手直接拼命令时的路径错误。模板与页面示例因此可以被当作可复制起点，而不是只能靠文档口头描述。

Q5 · 页面模板怎样处理无 JS 与窄屏启动？

基于 README 中的 CLI 模板和 .changeset/content-templates-noscript.md 可知，订单详情、工作项详情和组件文档等模板会先渲染窄屏首屏，避免桌面侧栏把移动端页面挤成窄列。脚本运行后，宽屏才恢复侧栏布局；窄屏主内容继续留在主列，文档分区链接也保持为顶部链接。这更像渐进增强：模板默认状态不依赖完整交互脚本。

来源：.changeset/content-templates-noscript.md

Q6 · 交互状态和可用性细节如何实现？

内容模板在退款、删除附件等破坏性动作前加入确认步骤，取消不改变状态，确认后才显示会发生什么的演示提示。useContainerReveal 一类布局钩子按粗指针设备处理可见性，不是简单把所有触摸屏都当成手机，以避免触屏笔记本接鼠标时行为误判。这些实现说明组件和模板把可访问性、状态和指针环境作为具体 prop 或 hook 行为处理，而不只靠 CSS。

来源：.changeset/content-confirm-steps.md .changeset/container-reveal-hook-template.md
