ag-ui-protocol/ag-ui★ 20,751

AG-UI 是一个把 AI 智能体接到前端应用的开放协议，解决各家 agent 框架输出不统一、页面只能靠临时接口接线的痛点。它适合已经用 LangChain、Mastra、CrewAI 等框架做出 agent，又需要把结果做进 Web、终端、聊天或移动端应用的工程师和团队。项目主要提供一条双向 typed event stream：一次对话由 RunAgentInput 触发，agent 流式返回文本、工具调用、状态、推理、子代理等事件，客户端按事件渲染即可；官方还给了 TypeScript、Python、.NET SDK、CLI 模板、Dojo 示例和多种框架集成。它的特别之处是协议优先且传输无关，HTTP+SSE、Protobuf 或 middleware 都能承载同一套事件，因此同一 agent 可以换不同前端而不改业务逻辑。

Q1 · 客户端发起一次 agent 运行并渲染事件的主路径是什么？

来源：apps/client-cli-example/src/index.ts apps/client-cli-example/package.json

Q2 · AG-UI 的核心数据结构如何把 agent 能力拆成事件？

Q3 · shared state、frontend tool 和 human-in-the-loop 在协议里怎样实现？

README 把 shared state 设计成 typed store，通过 STATE_SNAPSHOT 和 STATE_DELTA 以 JSON Patch 同步。frontend tool 用 tool-call events 把参数送到 app，再把结果送回 agent，apps/client-cli-example/src/index.ts 中 onToolCallResultEvent 展示结果事件。human-in-the-loop 不是单独请求接口，而是 run 以 interrupt outcome 结束，用户批准后下一次 run 继续。

agent-browser 是一个给 AI agent 使用的浏览器自动化命令行工具，解决模型不能方便地打开网页、读取页面结构并点击输入表单的问题。它把浏览器操作拆成一条一条命令，用 snapshot 把页面压缩成带 @e1 这类引用的文本，随后用 click、fill、get 等命令对元素操作并再次读取结果，适合自动测试、网页信息提取、表单提交和 AI agent 驱动真实浏览器。项目提供大量命令，还能截图、录屏、读取 cookie、切换标签页、处理弹窗和网络状态，并带有 agent skills 与 MCP 入口。

实现逻辑

Q1 · agent-browser 的命令入口是怎样走到浏览器的？

main.rs 里先 parse_flags 和 parse_command 把 shell 参数整理成带 action、cdpUrl/cdpPort 等字段的命令对象，再从 connection 模块导入 ensure_daemon 和 send_command。README 说明第一条命令会启动后台 daemon，每条 CLI 命令发给 daemon，由 daemon 通过 Chrome DevTools Protocol 控制浏览器。响应会统一序列化成 JSON 文本输出。

来源：cli/src/main.rs cli/src/commands.rs cli/src/connection.rs README.md

Q2 · snapshot 和 ref 的核心数据结构是什么？

README 描述 snapshot 返回紧凑文本，每个元素带 @e1 这类 ref，用于后续 click、fill 等动作。目录中有 cli/src/native/snapshot.rs 和 cli/src/native/element.rs，基于 README/目录结构推断它们负责页面快照与元素定位的数据建模。ref 只在生成快照时的页面状态下有效，导航或 DOM 变化后需要重新 snapshot。

来源：README.md cli/src/native/snapshot.rs cli/src/native/element.rs

Q3 · 它如何对接不同浏览器和远程调试接口？

README 说明默认用 Chrome for Testing，也可通过 --cdp、--auto-connect、--engine、iOS Simulator 或云浏览器 provider 连接不同浏览器。main.rs 的 validate_cdp_flags 会检查 cdpUrl、cdpPort 和 CDP headers，并把这些设置放进 launch envelope 或 session settings patch。cli/src/native/cdp/client.rs 等模块提供了 CDP 通信的实现入口。

来源：README.md cli/src/main.rs cli/src/native/cdp/client.rs

Q4 · 会话状态和浏览器生命周期是如何管理的？

README 指出每个 --session 有自己的 daemon 和浏览器，daemon 在一小时无命令后默认关闭 headless browser 并退出，如果配置 session persistence 会先保存状态。目录中 cli/src/native/daemon.rs、cli/src/native/state.rs、cli/src/session_files.rs 和 cli/src/session_settings/store.rs 分别对应 daemon 生命周期、状态、会话文件和设置存储。

来源：README.md cli/src/native/daemon.rs cli/src/native/state.rs cli/src/session_files.rs cli/src/session_settings/store.rs

Q5 · 错误处理和并发有什么可见做法？

README 明确 click 在目标隐藏、禁用、超出视口或被覆盖时会失败，而不是误报成功；导航或 DOM 变化后旧 ref 失效也要重新 snapshot。main.rs 会输出 success:false、error、type 形式的 JSON 错误，方便 agent 判断下一步。AGENTS.md 的 e2e 测试要求单线程运行，以避开多个真实 Chrome 实例竞争资源。

来源：README.md cli/src/main.rs AGENTS.md

Q6 · 项目为什么把浏览器保持为有状态 daemon，而不是每次命令新开浏览器？

README 强调 agent 每次只执行一条短 shell 命令，浏览器在命令之间保持打开，这样每一步都能读取结果后再决定下一步，适合 agent 的逐步决策循环。main.rs 还支持 batch 和 relaunch 相关逻辑，说明单次调用也能携带多条命令或触发设置变化后的浏览器重启。这种取舍把复杂页面交互拆成可观察、可重试的小步骤。

来源：README.md cli/src/main.rs
