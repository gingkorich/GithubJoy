google-research/paper-orchestraPythondeep

PaperOrchestra 主要解决把研究想法和实验日志这类松散材料自动组织成投稿用 LaTeX 论文的问题，其实现通过命令行入口调用 methods 下的多代理流水线，依次处理大纲、文献综述、章节撰写、内容精修和可选绘图，并利用 utils 访问 Gemini 或 OpenAI、Semantic Scholar 及 PDF 工具，便于评估自动化程度与集成成本。

实现逻辑

Q1 · 项目如何从命令行入口组织论文生成调用链？

paper_writing_cli.py 先用 argparse 接收 raw materials、template、output、模型和 plotting 参数，再把 raw_materials_dir 拷贝进带时间戳的输出目录。若 --use_plotting 为真，它从 methods/paper_writer_with_plotting.py 导入 write_single_paper；否则从 methods/paper_writer.py 导入不带绘图流程的 write_single_paper。

来源：paper_writing_cli.py methods/paper_writer_with_plotting.py methods/paper_writer.py

Q2 · 多代理流水线的代码结构是怎么分层的？

核心代理放在 methods/agents 下，分别有 outline_agent.py、literature_review_agent.py、section_writing_agent.py、content_refinement_agent.py 和 plotting_agent.py。methods/prompts 为各代理保存提示词，例如 methods/prompts/outline_agent.py 与 methods/prompts/section_writing_agent.py，形成代理执行与指令模板分离。

来源：methods/agents/outline_agent.py methods/agents/literature_review_agent.py methods/agents/section_writing_agent.py methods/agents/content_refinement_agent.py methods/agents/plotting_agent.py methods/prompts/outline_agent.py methods/prompts/section_writing_agent.py

Q3 · 文献综述部分如何接入外部学术检索？

literature_review_agent.py 与 methods/prompts/literature_review_agent.py 共同承担文献查找、筛选和综述生成，utils/scholar_utils.py 提供学术检索辅助。CLI 中的 --research_cutoff 会把检索时间窗传入流水线，环境变量 SEMANTIC_SCHOLAR_API_KEY 说明实际后端依赖 Semantic Scholar。

来源：methods/agents/literature_review_agent.py methods/prompts/literature_review_agent.py utils/scholar_utils.py paper_writing_cli.py

Q4 · LLM 后端选择和模型参数如何传递？

paper_writing_cli.py 暴露 --writer_model_name、--reflection_model_name、--plotting_model_name 和 --image_model_name，并将这些参数传给 methods/paper_writer*.py。utils/llm_backend_utils.py、utils/gemini_utils.py 和 utils/openai_utils.py 共同覆盖 Gemini/OpenAI 调用，requirements.txt 也包含 google-genai 与 openai。

来源：paper_writing_cli.py utils/llm_backend_utils.py utils/gemini_utils.py utils/openai_utils.py requirements.txt

Q5 · 可选绘图流水线怎样与主生成流程组合？

CLI 通过 --use_plotting 切换到 methods/paper_writer_with_plotting.py，并传入 --plotting_model_name、--image_model_name 和 --plotting_max_critic_rounds。methods/agents/plotting_agent.py 负责绘图代理逻辑，requirements.txt 的 matplotlib、numpy、opencv-python 和 PyMuPDF 为其图像与 PDF 处理提供基础。

来源：paper_writing_cli.py methods/paper_writer_with_plotting.py methods/agents/plotting_agent.py requirements.txt

Q6 · Streamlit 前端与输出目录管理暴露了哪些实现取舍？

frontend/app.py 用 st.session_state 初始化 running、progress、logs、current_step、figures、error_message 等字段，并加载 frontend/examples/cvpr_example.json 示例。paper_writing_cli.py 在未提供 --output_dir 时自动创建带时间戳目录，并要求 raw_materials_dir 存在，否则 sys.exit(1)；在无 figures 且关闭 plotting 时只警告不阻断，以降低缺失素材时的使用门槛。

来源：frontend/app.py frontend/examples/cvpr_example.json paper_writing_cli.py templates/cvpr2025/template.tex templates/iclr2025/template.tex

sveltejs/svelteJavaScriptdeep

Svelte 是一个面向 Web 应用开发的 JavaScript 编译器，把声明式组件编译成直接更新文档对象的代码，以减少运行时开销；仓库按主包、文档、基准测试、变更集和消息目录组织，性能测试通过子进程隔离并输出结果文件供后续对比分析。

Q1 · 项目的主要入口和运行时调用链在给定材料中如何体现？

Q2 · 性能基准模块的核心数据结构是什么？

run.js 将 benchmarking 的 suites 建模为数组，每项包含 benchmarks 和 name，其中 benchmark 至少有 label 与 fn，fn 的结果通过 child process 以 message 返回 time 与 gc_time。compare/index.js 进一步把分支名映射为 .results/<branch>.json 与 .profiles/<branch>，形成按分支聚合的结果结构。

来源：benchmarking/run.js benchmarking/compare/index.js

Q3 · 构建、测试和发布依赖哪些外部工具？

来源：CONTRIBUTING.md package.json .changeset/config.json .github/workflows/ci.yml

Q4 · 基准测试如何避免进程污染并处理失败？

run.js 在 parent mode 下对每个 benchmark label 调用 fork，子进程通过 BENCH_SINGLE 环境变量只跑一条基准，退出前用 process.send 返回结果；如果子进程没有 message 就会以 code 非 0 被视为失败并 reject。compare/index.js 在退出时执行 git checkout ${original_ref} 恢复分支，并在 fork runner 时把 message 结果写入对应 JSON 文件。

来源：benchmarking/run.js benchmarking/compare/index.js

Q3 · 排除 selector 后，jQuery 的选择器实现会变成什么？

appwrite/appwritePHP/TypeScriptdeep

该平台把认证、数据库、存储、函数、实时等能力聚合在统一接口层，核心服务端使用协程框架与缓存队列拆分重任务，命令行入口通过依赖容器装配平台库和项目库，并记录链路追踪，适合自托管后端与智能代理调用。

实现逻辑

Q1 · CLI 任务入口如何从命令参数走到任务容器和协程执行？

app/cli.php 读取 argv 的第一个任务名，创建 Utopia CLI 并让 Appwrite 平台以 Service::TYPE_TASK 初始化。如果参数缺失，它会输出错误并以非零状态退出。随后 cache、pools、authorization、数据库工厂等对象被放入容器，最后通过 Swoole 协程运行 cli。

来源：app/cli.php

Q2 · 任务运行时如何决定用平台库还是项目库，并处理权限上下文？

容器注册了 dbForPlatform 和 getProjectDB：前者通过 DatabaseFactory 创建 console/platform 库，并在集合尚未存在时重试。后者根据传入的 Document $project 切换目标库，空项目或 console 会复用平台库。任务入口又显式创建 Authorization 并 disable，因此后台任务默认绕过普通资源鉴权。

来源：app/cli.php

Q3 · Dockerfile 如何把后端服务拆成可调度进程并提供持久化目录？

Dockerfile 复制 app、public、src、packages 等代码，并创建 uploads、functions、certificates、videos-tmp 等 /storage 目录。它还把 worker、worker-functions、worker-videos、realtime、schedule 等脚本标记为可执行，说明运行态由多个进程和队列协作处理请求。

来源：Dockerfile

Q4 · CLI 的错误与并发生命周期怎样收尾？

app/cli.php 使用 Runtime::enableCoroutine(SWOOLE_HOOK_ALL) 把同步代码挂到协程运行时。初始化动作会创建 task.$taskName span，错误动作记录异常、把 exitCode 设为 1 并清空 Swoole Timer。shutdown 动作再 finish 当前 span，从而让失败任务和退出码能被统一观察。

来源：app/cli.php

Q5 · 镜像里为什么还要单独编译 ffmpeg 与 Rust 扩展？

Dockerfile 用独立阶段从源码构建 ffmpeg 8.1.2，并安装 GnuTLS，以支持 videos worker 通过 https 读取源文件。它还会用 Cargo 构建 libutopia.so，供 PHP 侧扩展能力使用，避免直接使用 Alpine 里较旧或不匹配的包。

来源：Dockerfile

技术栈
PHP/TypeScript / Utopia, Swoole, Appwrite Platform / Docker/Composer/Cargo
适用场景
  • 自托管后端即服务
  • 为 Web/Mobile 应用提供认证、数据库、存储与函数
  • 通过 MCP 让编码代理操作线上 Appwrite 项目
  • 处理实时事件、消息通知与站点部署
风险
  • 自托管涉及缓存、队列、数据库、worker 和多进程，运维复杂度较高
  • 后台任务入口显式 disable Authorization，脚本误用可能绕过普通权限边界
  • Dockerfile 包含源码构建 ffmpeg 与 Rust 扩展，镜像供应链和 ABI 维护成本较高
  • 安装流程挂载 docker.sock 并监听安装端口，生产网络配置不当会扩大攻击面
